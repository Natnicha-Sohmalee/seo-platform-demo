1. ส่วนประกอบและการไหลของข้อมูล

เว็บและฐานข้อมูลอยู่บนเครื่องลูกค้า การอ่านเว็บไซต์และเรียก AI เป็นการเชื่อมต่อออกอินเทอร์เน็ต

ผู้ใช้งานBrowser ของลูกค้า

กรอกข้อมูล เลือกงาน ตรวจ แก้ และดาวน์โหลดบทความ

ในเครื่อง · Next.jsหน้าเว็บ + API

ตรวจบัญชี รับคำสั่ง และประสานการอ่านเว็บ/AI

ในเครื่อง · SupabaseAuth + Postgres

เก็บบัญชี โปรเจกต์ งานอ่านเว็บ และงานเนื้อหา

ในเครื่อง · FastAPIPython Worker

อ่านเว็บไซต์ที่สั่งและบันทึกผลแต่ละหน้า

ออนไลน์เว็บไซต์สาธารณะ

แหล่งข้อมูลที่ลูกค้าเลือกให้ Worker อ่าน

ออนไลน์Gemini หรือ Typhoon

รับบริบทที่เลือกและส่งผลลัพธ์กลับไปที่เว็บ

เปิดและบันทึกงานBrowser ↔ Next.js / Supabase local · งานเดิมอ่านจากฐานข้อมูลโดยไม่เรียก AI ใหม่
อ่านเว็บไซต์Browser → POST /api/crawl → Worker → เว็บไซต์สาธารณะ → Worker บันทึกหน้าใน Supabase local
ติดตามงานBrowser → GET /api/crawl/:jobId → Next.js อ่านสถานะและหน้าจาก Supabase local
สร้างเนื้อหาBrowser → POST /api/content-brief → AI provider → ผลกลับหน้าเว็บให้ตรวจ/แก้ → บันทึกใน Supabase local
งานหน้าเว็บงาน Workerงานฐานข้อมูลงาน AI

2. เส้นทางที่ต้องใช้งานได้ครบ

สองทางเข้าจบที่บทความ Markdown เหมือนกัน คีย์เวิร์ดจาก CSV ใช้ประกอบได้ทั้งสองทาง

มีเว็บไซต์โปรเจกต์ → Crawl → แผน → บทความ

อ่านหน้าเว็บ ดูผล SEO เลือกหน้าเป็นแหล่งข้อมูล แล้วสร้างแผนและบทความ ลูกค้าตรวจ แก้ บันทึก เปิดต่อ และดาวน์โหลด

ไม่มีเว็บไซต์โปรเจกต์ → ข้อมูลธุรกิจ → แผน → บทความ

สร้างโปรเจกต์โดยไม่มี URL กรอกธุรกิจและกลุ่มเป้าหมาย แล้วทำแผนและบทความได้ทันที

CSV เป็นทางเลือก: นำเข้าชุดคีย์เวิร์ดพร้อมที่มา/ช่วงข้อมูลและเลือกคำสำหรับแผน ระบบไม่อ้างว่าตัวเลขในไฟล์เป็นข้อมูลล่าสุด

UI1 · ไม่มีเว็บDATA1 · แผนDATA2 · บทความV1 · ตรวจมีเว็บV2 · ตรวจไม่มีเว็บ

3. โปรเจกต์เป็นขอบเขตของข้อมูล

หนึ่งธุรกิจใช้หนึ่งบัญชีใน pilot ทุกงานเนื้อหาอยู่ในโปรเจกต์ เว็บไซต์เป็นข้อมูลที่ไม่บังคับ

โปรเจกต์เจ้าของคือบัญชีลูกค้า · website_url ว่างได้
งานอ่านเว็บcrawl_jobs → crawl_pages
ชุดคีย์เวิร์ดข้อมูลจาก CSV + ที่มา
แผนบทความบริบทและแหล่งข้อมูล
บทความร่างที่แก้และส่งออกได้
ข้อมูลสภาพปัจจุบันใน branchเป้าหมายใน pilot
projectsผูกกับ user_id; สร้างโปรเจกต์ต้องมี URLwebsite_url ว่างได้; เป็นขอบเขตของงานทั้งหมด
crawl_jobs / crawl_pagesงานผูกโปรเจกต์แล้ว; Worker เขียนผลหน้าเว็บรักษาความสัมพันธ์และ unique (crawl_job_id, url); จัดการงานค้างหลัง restart
content_briefsเก็บแผนและชุดคีย์เวิร์ดตาม storage_key ระดับบัญชีเพิ่ม project_id และกรองงานตามโปรเจกต์
articlesเก็บบทความตาม storage_key ระดับบัญชีเพิ่ม project_id; รักษา version กันการบันทึกชนกัน
AI usage / consentยังไม่มีตาราง/การบังคับใช้เก็บจำนวนคำขอและหลักฐานยินยอม โดยไม่เก็บ key หรือ prompt

สำคัญ: ต้องมี SQL migration ใน repo ที่สร้าง schema และ RLS ซ้ำได้ ปัจจุบัน repo ยังไม่มี migration สำหรับฐานข้อมูลใหม่

DB1 · Local stackDB2 · MigrationDATA1 · แผนDATA2 · บทความ

4. จุดเชื่อมที่ intern จะเจอในโค้ด

อ่านจากฝั่งซ้ายไปขวาเพื่อรู้ว่า request เริ่มตรงไหน ไปที่ใด และผลถูกเก็บอย่างไร

จุดเชื่อมทำหน้าที่เริ่มดูจากไฟล์
POST /api/crawlตรวจบัญชี/โปรเจกต์/URL → สร้าง job ใน DB → ส่งให้ Workersrc/app/api/crawl/route.ts
GET /api/crawl/:jobIdอ่านสถานะและหน้าเว็บจาก DB พร้อมตรวจเจ้าของโปรเจกต์src/app/api/crawl/[jobId]/route.ts
POST /jobs (Worker)รับงาน crawl แล้วอ่าน/บันทึกผลทีละหน้าworker/api.py · worker/supabase_store.py
POST /api/content-briefaction recommend, brief, article → AI providersrc/app/api/content-brief/route.ts · src/lib/ai-provider.ts
อ่าน/บันทึกงานเนื้อหาเว็บใช้ Supabase client; ตรวจ user_id และ versionsrc/lib/content-storage.ts
งาน Workerงานหน้าเว็บงาน AI

5. กติกาที่งานทุกส่วนต้องรักษา

สิ่งเหล่านี้เป็นเงื่อนไขของ pilot ไม่ใช่แค่รายละเอียดในโค้ด

สิทธิ์บัญชีหนึ่งเห็นเฉพาะงานของตน

RLS และการตรวจเจ้าของโปรเจกต์ใน API ต้องสอดคล้องกัน แม้ pilot ใช้ลูกค้าเพียงบัญชีเดียวก็ทดสอบด้วยบัญชีที่สอง

Crawlอ่านเฉพาะเว็บไซต์สาธารณะ

การยอมรับ HTTP ของ Supabase local สำหรับ Worker ห้ามทำให้ตัวกรอง URL เป้าหมาย crawl ยอมรับ localhost/private network

AIแจ้งข้อมูลและจำกัดคำขอ

ข้อมูลจริงต้องยินยอมก่อนส่ง; จองสิทธิ์แบบ atomic ก่อนเรียก provider; เกินเพดานต้องไม่มี request ออก

บันทึกงานเปิดต่อโดยไม่สร้างใหม่

การเปิดแผนหรือบทความเดิมไม่เรียก AI เอง และ version ต้องกันแท็บหนึ่งเขียนทับงานล่าสุดของอีกแท็บ

DB2 · สิทธิ์WK1 · URLAI1 · ยินยอมAI2 · เพดาน

6. AI ส่งอะไรออกไป และคุมอย่างไร

ทีมเลือก provider ผ่าน server env ตอนติดตั้ง ลูกค้าเห็นชื่อ provider และประเภทข้อมูลก่อนกดใช้งาน

GeminiApp limit + project spend cap

ใช้คีย์/โปรเจกต์เฉพาะ pilot; ตั้งเพดานในแอปและ spend cap ที่ provider โดยตรวจค่าจริงจากบัญชีทีมก่อนส่งมอบ

TyphoonApp limit เป็นหลัก

ใช้คีย์เฉพาะ pilot; rate limit ของ provider จำกัดความถี่ ไม่ใช่เพดานการใช้รวมที่ยืนยันแล้ว

ข้อมูลที่ส่ง: รายละเอียดธุรกิจ หัวข้อ กลุ่มเป้าหมาย คีย์เวิร์ดที่เลือก ข้อความจากหน้าที่เลือก และแผนบทความเมื่อสร้างบทความ คีย์ API อยู่ฝั่ง server; ผู้ดูแลเครื่องลูกค้ายังเข้าถึงค่า env ในเครื่องได้ จึงใช้คีย์เฉพาะ pilot และเพิกถอนเมื่อจบ

AI1 · แจ้งข้อมูลAI2 · เพดานAI3 · สอง provider

7. ติดตั้งบนเครื่องลูกค้า

ทีมติดตั้งครั้งแรก ลูกค้าเปิด/ปิดและใช้เองภายหลัง

ส่วนรันที่ไหนสิ่งที่ต้องตั้ง/ตรวจ
BrowserWindows เครื่องลูกค้าเปิดเว็บที่ http://localhost:3000
Next.jsLinux ใน WSLSupabase local URL/key, Worker URL/key, AI provider/key; secret ไม่ commit
Python WorkerLinux ใน WSLSupabase local URL/key และ Worker API key; ตรวจ /health
Supabase localDocker บนเครื่องลูกค้าAuth/Postgres/API และ migration จาก repo; bind ให้เข้าถึงเฉพาะเครื่องที่ต้องใช้
AI / เว็บไซต์เป้าหมายอินเทอร์เน็ตการเชื่อมต่อและสิทธิ์ของคีย์/เว็บไซต์

ข้อจำกัด: Supabase local stack ใช้กับ pilot ที่ข้อมูลทดลองเริ่มใหม่ได้ ไม่ใช่ฐาน production; รอบนี้ไม่ทำ backup ก่อนใช้จริงต้องออกแบบและทดสอบ backup/restore

DB1 · Local stackOPS1 · เปิด/ปิดOPS2 · Bootstrap

8. เมื่อบางส่วนไม่พร้อม

Intern ใช้ตารางนี้กำหนดข้อความและทางไปต่อ ไม่ปล่อยให้ผู้ใช้เดาว่างานสำเร็จหรือไม่

เหตุการณ์ผลที่ต้องเห็นใน PilotTask
Worker ปิดหรือรับงานอยู่แจ้งว่าเริ่ม crawl ไม่ได้/คิวเต็ม และให้ตรวจประวัติก่อนลองใหม่WK1, V3
ปิดระบบกลาง crawlงานเดิมไม่แสดง running ตลอดไป; หน้าที่บันทึกแล้วคงอยู่WK2
AI 429 หรือ timeoutแจ้งว่า provider ไม่พร้อม; เก็บงานเดิมไว้ และไม่สร้างผลปลอมV3
AI ครบเพดานหยุดก่อนส่ง request และแสดงจำนวนสิทธิ์คงเหลือ/เหตุผลAI2
URL crawl ถูกปฏิเสธแสดงเหตุผล ไม่พยายามอ่าน private/localhostWK1, V3

9. ภาพรวมเกณฑ์ส่งมอบ

  1. ติดตั้งจาก clone ใหม่บนเครื่องเป้าหมายได้โดยไม่ต้องเดา schema หรือ URL
  2. ลูกค้าทำเส้นทางมีเว็บและไม่มีเว็บจนแก้ บันทึก เปิดต่อ และดาวน์โหลด Markdown ได้
  3. บัญชีอื่นอ่าน/แก้งานของลูกค้าไม่ได้; AI ไม่ถูกเรียกเมื่อยังไม่ยินยอมหรือเกินเพดาน
  4. กรณี Worker/AI ไม่พร้อมและ restart กลางงานมีสถานะกับทางไปต่อที่ชัดเจน
